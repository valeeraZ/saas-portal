# Runtime Registry validation

## Scope and reproduction

Branches: Admin and Portal `codex/runtime-application-registry`, based on `5219dc8` and `e0e177f`. No Auth/SDK source changes are required. Use Node 24.10+, PostgreSQL and installed dependencies in both repositories.

```sh
# saas-admin
npm ci
npm test
npm run typecheck
npm run contracts
npm run format:check

# saas-portal
npm ci
npm test
npm run typecheck
npm run build
npm run format:check
ADMIN_SOURCE=/absolute/path/to/saas-admin \
REGISTRY_TEST_DATABASE_URL=postgresql://test_owner@127.0.0.1:59534/postgres \
npm run test:runtime-registry
```

The PostgreSQL URL must identify a disposable development/test cluster and a role allowed to create databases. The test creates three random `registry_*` databases for Admin, Portal and example-app data; it drops only those databases in cleanup. It binds random loopback ports, generates signing/session keys in a temporary directory, starts two real Admin APIs and two production-built Portal processes, and cleans up its own processes. It does not read `.env.local`, reuse business tables or send email. Test Auth is an in-process protocol stub and Portal sessions are inserted through the real encrypted session store; this suite is not a new Keycloak login/end-to-end identity claim.

For actual Next.js browser coverage, prepare an isolated packed-SDK consumer using SDK `npm run pack && npm run test:tenant-next`, then supply its directory (from SDK `artifacts/tenant-next-consumer.json`):

```sh
ADMIN_SOURCE=/absolute/path/to/saas-admin \
REGISTRY_TEST_DATABASE_URL=postgresql://test_owner@127.0.0.1:59534/postgres \
SAAS_TENANT_CONSUMER=/absolute/path/to/isolated-consumer \
PORTAL_CHROMIUM=/absolute/path/to/chromium \
npm run test:runtime-registry
```

The optional test generates one stable `NEXT_SERVER_ACTIONS_ENCRYPTION_KEY` per application and supplies it to each retained build (not to Registry), following [Next.js self-hosting guidance](https://nextjs.org/docs/app/guides/self-hosting#server-functions-encryption-key). Without this setting, independent builds change action identities and the old-tab action test fails even though its assets remain available.

The optional test copies consumer source/lockfiles into its own temporary directories, installs packed dependencies, builds two versions of `next-reports` plus `next-metrics`, and uses real SDK signature/deployment/replay validation. It registers them after Portal has started. The consumer path must contain `next-reports` and `next-metrics` generated by the current SDK tenant scaffold, with resolvable tarball dependencies. Chromium may be omitted when Playwright's matching browser is installed.

## Operational limits

Approval is a privileged operator attestation after external artifact/health checks; no automated readiness worker or web management UI is implemented. Deployment/asset-version facts are immutable, but operators must keep the upstream artifact immutable and the old origin alive during retention. Retaining old JS/CSS/fonts does not automatically provide compatibility for arbitrary breaking API or Server Action changes; the optional test exercises compatible releases of the same app.

TTL is zero. A resolution begun after a committed primary-database revocation cannot reuse an old positive response. A previously authorized request can remain in flight for at most the existing 30-second Portal response window. Downloaded assets and already-completed writes cannot be revoked retroactively. Do not add CDN caching or use lagging Admin database read replicas. Network egress policy, real TLS/DNS operations, real-Keycloak identity regression and production rollout are separate from this disposable test.
